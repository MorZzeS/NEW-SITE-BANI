## Backup consistency, retention and restore verification

Backup uses REPEATABLE READ transaction for a consistent environment-specific snapshot of four InnoDB tables, serializes binary hashes as base64, streams individually AES-256-GCM authenticated records with random IVs, and writes private exclusive 0600 .partial output. Footer records counts. Every encrypted record and count is re-read/decrypted before atomic rename to .jsonl.enc; failure removes incomplete output and reports only a fixed code. No plaintext dump, shell, command-line password or external service is used. Require openssl PHP extension in addition to listed extensions. Large datasets/runtime limits, disk-full handling and filesystem permissions still need isolated integration testing. A backup is not evidence of a successful restore.

Retention is one environment-scoped transaction: owner-configured ages govern journal, terminal outbox, leads and rate buckets separately. pending/processing/retry/unknown outbox are never deleted automatically, and their consent journal is retained; manual reconciliation is mandatory. Leads remain while any journal/outbox dependency exists, so effective lifetime can exceed configured lead duration. Approval must explicitly account for this. outbox.created_at is new in this candidate schema; no deployed schema altered. Production migrations require separately approved reviewed DDL. Backup cleanup is separate filesystem work AFTER DB commit: errors may mean DB cleanup committed but backup cleanup incomplete. Only correctly named generated regular files inside private backup_dir qualify; symlinks excluded. No approved time values are invented.
